# whubへのグラフモデル適用案

## 目的・前提・方針案
- 目的: backlog・FOCUS・task-planningを含む長期戦略と実行管理へ、グラフの考え方を適用できるか検討する
- 背景: [AIエージェントが使う5種類のグラフ](../../vault/literature/sources/AIエージェントが使う5種類のグラフ.md)
- 前提: 現時点では構想段階であり、データモデル・SSOT・グラフDB採用・実装範囲を確定しない
- 課題: backlog・task-planningは役割が異なるため統合できない一方、管理箇所が散り横断アクセスしにくい
- 課題: Phase・Step・依存・優先度がテキストに留まり、見落としによる順序違反を仕組みで防げない
- 目標: Web appでProjectごとのTask候補と着手可否を把握し、次に取り組む対象を即座に決められるようにする
- 目標: 知識・何をやるか・実行フロー・状態を分離し、whubの戦略・計画・実行基盤として組み込む
- 方針案: Markdownのナラティブと各文書の役割を維持しつつ、関係・状態・制約を構造化する
- MVP: ユーザーが会話セッションを開始し、AIによるBacklogのTask化・優先度・依存・計画案を確認、修正、承認する
- MVP: 現行のtask md・backlog・Skillを置き換えず、運用に接続しないシャドーDBとして構築する
- MVP: 新規のデモ用Project・Taskを会話経由で登録し、既存文書の取込・同期は行わない
- MVP: Project内のTask間依存と、Task状態・依存に基づく着手可否の判定を扱う
- MVP: Web appでProjectごとのTaskタイトル・優先度・着手可否を参照できるようにする
- MVP対象外: Project横断依存、TaskをまたぐPhase・Step依存、既存task md・backlogとの同期
- 粒度原則: Task外部とのPhase・Step依存が必要な場合は、Taskの分割・粒度を見直す
- 状態原則: `blocked`をTask状態として保存せず、Task自身の状態と未完了依存から`actionable`を導出する
- MVP着手不可理由: 未完了依存を表す`incomplete_dependencies`だけを扱い、承認待ち・一時停止などは将来検討する
- 将来案: Backlog追加時の提案生成と承認依頼を段階的に自動化する
- 将来案: Project横断依存を追加できるよう、MVPでもTaskを一意に識別できる設計を検討する
- 実行方針: 自動化範囲はTaskごと・実行セッションごとに相談し、受け入れ条件を固められるPhaseだけ自動化する
- ガード: 未完了の依存を飛ばす着手は、人間・AIのどちらが主体でもブロックする
- 計画変更: 状況変化時は理由付き変更案を承認してからグラフを更新し、単純な強制実行は許可しない
- 自動実行: 計画から外れる必要を検出したらTaskを停止し、変更したい方向と理由を提案して承認を待つ
