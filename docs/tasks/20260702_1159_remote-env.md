# 目的・前提・方針案

## 目的
リモートリソースの開発体験を「リモートファースト＋SSHFS参照マウント」で整備する。Mac切断後もAgent・長時間処理が継続し、単一ツリーでプロジェクト横断コンテキストをAIに渡せる。

## 前提
- SSHFSを復活する：AppleDouble汚染は`noappledouble`で回避、レイテンシ弱点は重い走査のリモート委譲（CodeGraphはSSH実行済み）で実質無効化と再評価（経緯は試行2・ADR 0008）
- 対象は自宅サーバのみ。スパコンはログインノードの常駐プロセス制約のため対象外
- 既存SSH基盤（`remote.py`の`build_ssh_command`/`run_ssh_command`）を流用する
- 経緯は`docs/roadmap.md`に記載済み。方式決定はADR 0008へ記録する

## 確定した意思決定
- **1タスク（1md）で全Phaseを扱う**
- **Mutagen不採用**：リモートAgent稼働中のローカル編集で双方向同期の構造的コンフリクトが必然のため全廃
- **用途分担**：編集・コード確認・横断コンテキスト参照=mount／走査・長時間実行=リモートへコマンド投げ or `whub cd`→claude／大容量の手元確認=`whub fetch`
- **`whub cd`のremoteはtmuxをデフォルト**にし、素シェルへのエスケープオプションを残す
- **tmuxセッション命名は`whub-<project>`**
- **スクロールバック問題はtmux設定で吸収**（screen時代の不便への対策。`mouse on`＋`history-limit`でホイール遡りを可能にする）
- 無人Agent運用のpermission設計は本タスクの対象外（別途起票）

## 案（実装時に確定）
- 同時複数接続の独立ビュー：grouped session＋`destroy-unattached`（detach時に自動掃除）
- tmux設定の適用方式：セッション作成時に`set-option`注入 or リモート`~/.tmux.conf`配布（boot連携）
- マウントオプション詳細（`reconnect,ServerAliveInterval=15,ServerAliveCountMax=3`等）とstale検知方式（timeout付きチェック）
- ~~旧MountResourceを復元するか現行RemoteResourceへmount設定を統合するか~~ → RemoteResourceへ統合・必須フィールド化で確定
- エスケープオプション名：`--plain`
- リモートにtmuxが無い場合：cdは素シェルfallback＋警告
- fetch先：`.whub/downloads/<resource>/`

# 実行ログ

### 試行 1: tmuxスニペットビルダーの置き場
- 実施内容: cd.py内ヘルパー→remote.py→専用モジュールの順に検討
- 結果: `src/whub/tmux.py`を新設（remote.pyのargvビルダーとはレイヤーが異なる。命名規約`whub-<project>`はPhase 4のstatusでも必要）。whub-conceptsのCLI設計ポリシーへ1行追記
- 判断: 方針変更

### 試行 2: 編集体験の方式再検討（Mutagen→SSHFS復活）
- 実施内容: Mutagen双方向同期・エディタリモーティング（vscode-server）・SSHFS復活を比較評価
- 結果: リモートAgent稼働中のローカル編集では双方向同期のコンフリクトが構造的に必然。目的を「横断コンテキスト取得」と再定義すると、重い走査はリモート委譲済み（CodeGraphはSSH実行）のためSSHFSのレイテンシ弱点は実質無効化。エディタリモーティングはプロプライエタリなvscode-server依存のため見送り
- 判断: 方針変更（Phase 2をsync→SSHFS復活へ差し替え、Mutagen全廃。用途分担=編集・横断コンテキスト:mount／走査・長時間実行:リモート実行／大容量:fetch）

### 試行 3: workspace_pathのスキーマ形
- 実施内容: RemoteResourceのworkspace_pathをOptional（None=mount対象外）として実装
- 結果: 「リモートも全てツリーに配置する」コンセプトに反するため必須へ変更。検証ルールはAnnotated型`WorkspacePath`としてsymlinkと共有
- 判断: 方針変更（必須化。manifest.yamlの全remote resourceへの記入が完了するまでwhubはバリデーションエラーになる）

### 試行 4: `whub run`復活の追加起票
- 実施内容: 「走査系はリモートへコマンドを投げる」の実体が生SSHしかないことを確認。過去に`whub run`が存在し（`405a866`）、schema v2リファクタで削除されていたと判明
- 結果: manifest経由のhost/path解決を伴うワンショット実行口として復活を決定。無人Agentのpermission設計（allowlistでのパターン許可）の布石も兼ねる
- 判断: 方針変更（Phase 2.5として追加。対話セッション=cd／ワンショット=runの線引き）
